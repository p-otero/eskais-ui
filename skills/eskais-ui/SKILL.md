# Eskais UI

Eskais UI components are UI SDK parts styled with Tailwind v4 and semantic tokens, copied into your project as source. Load the `ui-sdk` skill as well: everything it says about parts, controllers, change details and agents applies here unchanged.

## Install

1. In `components.json`, add the registry once:
   `"registries": { "@eskais": "https://raw.githubusercontent.com/p-otero/eskais-ui/<ref>/public/r/{name}.json" }`, where `<ref>` is a tag like `v0.1.0`, or `main`.
2. Aliases: shadcn writes `registry:ui` files to `aliases.ui` and `registry:lib` files to `aliases.lib`, and rewrites the registry's `@/components/ui`, `@/lib` and `@/lib/utils` imports to `ui`, `lib` and `utils`, so any prefix works. Set `components`, `ui`, `utils` and `lib` (e.g. `"~/components"`, `"~/components/ui"`, `"~/lib/utils"`, `"~/lib"`), and make each resolve through `compilerOptions.paths` in the root `tsconfig.json`: shadcn ignores `tsconfig.app.json` and `references`, and writes into a literal `@/` folder when an alias doesn't resolve.
3. Put `@layer ui-sdk;` as the first line of the global stylesheet, above `@import "tailwindcss"`.
4. `npx shadcn@latest add @eskais/theme @eskais/font-geist @eskais/button` (any item; dependencies come along). `font-geist` bundles the default font from npm; without it the theme falls back to the system font. `font-inter` is the alternative.
5. Subpath imports work too: `"imports": { "#ui/*": "./src/components/ui/*", "#lib/*": "./src/lib/*", … }` in `package.json` with aliases `#ui`, `#lib`…, and `allowImportingTsExtensions`. Keep the extension out of the mapping: `ui` holds `.ts` and `.tsx` files, and shadcn writes the extension into each import (see the README). A `ui/` folder is optional: for a flat `src/components`, map `#ui/*` and `#components/*` to the same folder. shadcn then writes the imports between registry files as `#components/x.tsx` (the first alias that matches), not `#ui/x.tsx`; both resolve, so your own code can use either.
6. `theme` brings `utils`. Merge classes with its `cn` (`@/lib/utils`), never another one: it knows the theme's utilities, and a plain tailwind-merge drops `text-meta` from `cn("text-meta", "text-muted-foreground")`. Over a `lib/utils.ts` that `shadcn init` wrote, add with `--overwrite`.

## Fast links

`Link`, `ButtonLink` and `NavigationMenuLink` follow a same-origin link on a primary mouse **press** (`pointerdown`), not on release, with `@fast-link/core`. Breadcrumb, Sidebar items, DocsPager, SiteHeader, SiteFooter, MobileNav and MarkdownView links get it through them (DocsToc too, but its in-page anchors stay native). `FastLinkRegion` (or `useFastLink()`, a ref) does the same for plain anchors in prose or rendered HTML.

- Keyboard, touch, pen, modified, middle and right presses, `target="_blank"`, `download`, external and cross-origin links and in-page anchors (`#section`) stay native, and so does a press that starts on a nested button or input.
- **Hash routers.** An `href` that starts with `#/` is a hash route and follows on press too: through `onFollow`, or by setting `location.hash`. Any other `#…` is an in-page anchor. Another router's prefix goes in `data-fast-link-hash-prefix` on any ancestor (`<body data-fast-link-hash-prefix="#!/">`) or `FastLinkRegion hashPrefix`; an empty value (`hashPrefix={false}`) makes every `#…` href an anchor.
- Navigation goes through `onFollow` when it's set (a router), and through `location.assign` otherwise. A `render`ed router link or a link with its own `onClick` acts on the click, so without `onFollow` it stays native rather than navigate twice; pass `onFollow` to route on press.
- Opt out per link with `fast={false}`, per region with `data-no-fast-link` on any ancestor, or for the whole app with `<body data-no-fast-link>`.
- **Navigation only.** A press can't be cancelled by moving the pointer away (WCAG 2.5.2 Pointer Cancellation); that's acceptable for navigation, which Back undoes, and never for an action. Buttons, menu items, `DialogTrigger`s and links that confirm, submit or change something stay on click: give such a link `fast={false}`. A site that must conform to WCAG 2.5.2 strictly sets `data-no-fast-link` on `<body>`.

## Keyboard and long lists

- **Shortcuts.** `useShortcut` registers in UI SDK's shared `shortcuts` (reuse UI SDK's own `shortcut` props on triggers; `useShortcut` is for the rest). Plain keys never fire while typing in an input, textarea or contenteditable, nor during IME composition; a modal pauses page shortcuts. A space makes a sequence (`g i`). A symbol or digit (`?`, `/`, `1`) matches the character typed, whatever Shift, AltGr or Option the layout needed; letters keep exact modifiers. Give each a `description` so `ShortcutsDialog` lists it; `extra` adds rows for keys that aren't registered, like a list's j/k. `formatShortcutSteps(keys)` formats them.
- **Scopes.** `<ShortcutScope name label>` is active while focus is inside (`active="focus"`), or while mounted (`active`), like an open panel. Shortcuts inside take its scope; `scope: null` makes one global.
- **People only.** Shortcuts add nothing for agents: they press the same buttons and menu items by name. Hints are `aria-hidden` `Kbd`; controls get `aria-keyshortcuts` (single steps only). A `Button` with an `aria-label` and a visible hint fails axe's label-content-name-mismatch: put the hint beside it, as `SidePanel` does, or `shortcutHint={false}`.
- **Collections.** `List` (link or button rows), the AgentTaskBoard table and backlog, and `DataTable` give rows one tab stop through `row-navigation` (UI SDK roving focus, no role added): ↓/j and ↑/k move, Home/End and PageUp/PageDown jump, Enter opens (the row's link or button, or `DataTable onRowOpen`), Space or x toggle selection where there is one (`List checkedIds`, `DataTable selectable`). The row moved to scrolls in with the least scrolling. A selectable `List` is a UI SDK Listbox, which moves itself; j/k and the page keys map onto its arrows.
- **Virtualization.** `virtual-rows` (TanStack Virtual) renders rows in document flow between `aria-hidden` gaps, so `ul > li` and `tbody > tr` stay valid; list rows carry `aria-setsize`/`aria-posinset`, table rows `aria-rowindex` under `aria-rowcount`. It scrolls with the nearest scrolling ancestor, else the window: give the list a bounded height (`min-h-0 flex-1 overflow-y-auto` parent, or `className="max-h-96"` on a DataTable). The focused row stays rendered, agents' `select`/`setSelection` take ids that aren't rendered, and the text of unrendered rows sits in `hidden="until-found"` stubs so find in page reaches them. Cards and grouped lists don't virtualize.
- **Cost.** On a 2,000-row list (`node tooling/list-bench.mjs` after `bun run build:showcase`), the first paint takes about 100 ms instead of 800 ms, and j/k reach the next paint in under 16 ms at the 95th percentile on a desktop CPU. Keep `renderItem` cheap: rows are memoized, so scrolling renders only the rows that enter.

## Global search (⌘K)

A search that loads results from the server, opened from the `Topbar` with `mod+k`. Only the triggers go in the Topbar's slots; the `CommandDialog` goes beside the `Topbar`, bound by the same controller:

```tsx
import { useAsyncOptions } from "@ui-sdk/react/async-options"

function AppTopbar() {
  const [search] = useState(() => createCommandDialogController())
  return (
    <>
      <Topbar
        center={
          <CommandDialogTrigger controller={search} shortcut="mod+k">
            <SearchIcon />
            Search the workspace
            <CommandDialogShortcut />
          </CommandDialogTrigger>
        }
        centerCompact={
          <CommandDialogOpenButton controller={search} variant="ghost" size="icon" aria-label="Search the workspace">
            <SearchIcon />
          </CommandDialogOpenButton>
        }
      />
      <GlobalSearch controller={search} />
    </>
  )
}

function GlobalSearch({ controller }: { controller: CommandDialogController }) {
  const results = useAsyncOptions(searchWorkspace, { debounce: 200, immediate: true }) // (query, { signal }) => Promise<{ value, label }[]>
  return (
    <CommandDialog controller={controller}>
      <CommandDialogContent title="Search the workspace">
        <Command
          filter={false}
          status={results.status}
          onQueryChange={(query) => results.setQuery(query)}
          onLoadMore={results.loadMore}
          onAction={(value) => {
            navigate(value)
            controller.close()
          }}
        >
          <CommandInput aria-label="Search the workspace" />
          <CommandStatus>{(state) => (state.loading ? "Searching…" : `${state.count} results`)}</CommandStatus>
          <CommandEmpty>
            {(state) => (state.empty && !state.loading ? `Nothing matches “${state.query}”` : null)}
          </CommandEmpty>
          <CommandList>
            {results.items.map((item) => (
              <CommandItem key={item.value} value={item.value} label={item.label}>
                {item.label}
              </CommandItem>
            ))}
          </CommandList>
        </Command>
      </CommandDialogContent>
    </CommandDialog>
  )
}
```

- **Never put the dialog in a Topbar slot.** A dialog renders where it is placed (in the browser's top layer), and `center` is hidden on narrow screens once `centerCompact` is set, so a dialog inside it opens with no box. The same goes for any slot you hide with `narrow:hidden`. The triggers can live anywhere: the main trigger's `mod+k` still listens while its slot is hidden.
- Every `options`, `items`, `stages`, `steps` and `columns` prop in the registry takes a readonly array, so `as const` data and `useAsyncOptions` results pass as they are. UI SDK 0.1.0-beta.5's `useAsyncOptions` itself still types its loader's result as a mutable array: return `[...rows]` from a loader whose source is readonly.
- `filter={false}` keeps the server's order; `useAsyncOptions` debounces, aborts stale requests through `signal` and keeps the last results while loading. Pass `status` so the list gets `aria-busy` and `CommandStatus` announces counts.
- The dialog returns focus to the trigger that opened it, and `onOpenChange` on `CommandDialog` reports both ways. `shortcut` is opt-in and only listens while the trigger is mounted.
- Outside a Topbar, prefer one trigger whose text goes `narrow:sr-only`. For a second way in, like a `Topbar`'s `centerCompact` icon, use `CommandDialogOpenButton` as above: it opens through the controller, gets focus back on close, and is hidden from agents, who open the dialog by its main trigger's name. Not a second `CommandDialogTrigger`: in UI SDK 0.1.0-beta.5 that drops the dialog's agent label.

## AgentTaskBoard

`npx shadcn add @eskais/agent-task-board` installs the board and every piece it uses.

- **Snapshot or live.** `mode="snapshot"` needs `generatedAt`: it is the board's "now", shown in a banner, and times never refresh. It shows no approve or reject actions. `mode="live"` refreshes times every 30 s, paused while the page is hidden; pass `now` only for tests and screenshots.
- **One clock.** The board calls `useNow` once and passes `now` down. When you compose `TaskCard` or `TaskDetailPanel` yourself, do the same: one `useNow()` per screen, never one timer per time.
- **Labels.** English by default. Override any string with `labels={{ columns: { done: "Shipped" } }}`, or pass `labels={agentTaskBoardLabelsEs}` from `@/components/ui/agent-task-board` for Spanish, including the pieces inside (status, liveness, usage, attempts). Pass `locale` and `timeZone` for formatting.
- **Agents.** The board's root exposes `selectTask`, `setView` (`"board"`, `"table"`, `"backlog"`), `filter` (`project`, `profile`, `model`, `query`, and `stage` as a list of stage ids, where `NO_STAGE` or the "No stage" label picks tasks without a location), `openThread` and `openLink` (`openLink(taskId, labelOrHref)`, with `onOpenLink`). A Button rendered as a link has no `press` for agents, so links open through that action. In live mode with `onApproveProposal`/`onRejectProposal`, `agentApproval` decides what an agent may do: `"confirm"` (default) asks a person through your bridge's `allow`, `"allow"` acts without asking, `"deny"` hides the actions from agents. People's buttons are the same either way.
- **Detail.** `detailPresentation="dialog"` (default) opens a selected task in an `xl` dialog, two columns from 56rem; `"drawer"` slides it in from the right; `"side"` keeps a non-modal panel so the board stays usable while reading. With a modal open, the board's controls are hidden from agents, but its `selectTask`, `filter` and `setView` still work.
- **Columns.** The collapse toggle ends each header (shown on hover, focus, touch or while collapsed). `columnAccent="tint"` (default) marks each column with its tone, `taskStatusAccentTones` overridden by `columnTones`; the status icons follow. Order comes from `columns`.
- **Links.** `TaskView.links` (`pull-request`, `branch`, `commit`, `issue`, `external`, with an optional `state`) list in the detail's side column; a card shows an icon link to its pull request. `renderLink` replaces each, `onOpenLink` takes over the click. A thread with `href` or `onOpenThread` gets an "Open thread" button with its id in the tooltip.
- **Attachments.** `TaskView.attachments` (the `Attachment` type of `@eskais/attachments`) show as an `AttachmentStrip` in the detail's main column, images opening a `Lightbox`; a card shows a paperclip count. Agents use the strip's `openAttachment(id)`. `renderAttachments(task)` replaces the strip.
- **Location.** Pass `stages` (the `Stage[]` of `@eskais/stage-track`, in order) and set `TaskView.location = { stage, href? }`: cards show a `StagePill`, the detail's side column a `StageTrack`, and the toolbar a `StageFilter` row with counts that sets `filters.stage`. Its last toggle, "No stage" (`labels.filters.noStage`), sets `NO_STAGE` (exported from the board) for tasks without a location; it shows when some task has none, and `stageFilterNone` forces it on or off. `renderLocation(task)` replaces the track.

A row opens the detail like a card. `renderBacklogActions(task)` adds your controls (a copy-command button) after Approve/Reject in each row, snapshot mode included; `renderCardActions(task)` does the same at the end of a card (pass a stable function: cards are memoized). - **State.** `view`, `filters`, `columns` and `selectedTaskId` are each controlled or uncontrolled (`defaultView`, `defaultFilters`, `defaultSelectedTaskId`). Cancelled tasks are hidden until `columns` shows them.

## Forms

`npx shadcn add @eskais/form` brings react-hook-form and `@hookform/resolvers`. The schema is any Standard Schema: Zod, Valibot, ArkType or Effect Schema.

- **Fields.** `<FormField name label description required>` wraps one control and binds it by `name`: `Input`, `Textarea`, `NumberInput`, `Select`, `Combobox`, `Checkbox`, `Switch`, `RadioGroup`, `Slider`, `DatePicker`, `SegmentedControl`, `ToggleGroup`, `TokenInput` (a `string[]` with `tokenType`). Checkbox and Switch bind `checked`, the rest `value`/`onValueChange`. A control's own module can add an adapter to `formControlAdapters` (exported from `field` and `form`). For your own control pass `bind="checked"`, an adapter, or `render={(field) => …}`; inside it, `useFormField()` returns `value`, `onChange`, `invalid`, `error`. Give every field a default value.
- **Required.** A field the schema rejects when empty gets an `aria-hidden` asterisk (`text-destructive`) and its control `required`. Detection probes the schema synchronously with the default values, so it needs a schema that reports every issue (Zod, Valibot, ArkType); otherwise pass `required`. `required={false}` drops the marker. `requiredLabel="required"` (on `Form` or `FormField`, in the page's language) adds words for screen readers; they join the field's name, so agents and `getByRole` see "Email required". Unset, screen readers announce the control's own required state.
- **Typed names.** `const { Form, FormField, useFormInstance, useFormWatch, useFormFieldArray } = createForm<typeof schema>()` at module level: the same components, with `name` checked against the schema's input (`tags.${number}.label` included).

  ```tsx
  const schema = z.object({ name: z.string().min(1), email: z.email() })
  const Profile = createForm<typeof schema>()

  <Profile.Form schema={schema} defaultValues={{ name: "", email: "" }} onSubmit={save} label="Profile">
    <Profile.FormField name="email" label="Email"><Input type="email" /></Profile.FormField>
  </Profile.Form>
  ```

- **Submit.** `onSubmit(values, { setError })` gets the parsed values. A returned Promise shows the submit Button's `loading`, disables the fields (`disableWhilePending={false}` keeps them) and ignores a second submit. Don't add your own pending state.
- **Server errors.** Throw `new FormServerError(message, { email: "Taken" })`, an object `{ fieldErrors, message }`, or a Standard Schema issue list (`toFormErrors` reads all three). Field errors land on their fields; the message, and errors for fields that aren't rendered, in `<FormRootError />` (an `Alert tone="destructive" live`). Any other error shows its `message` there. Focus then moves to the first invalid field, or to the root error.
- **Messages.** English by default. `messages={formMessagesEs}`, your own dictionary (strings with `{min}`, `{max}`, `{label}`, or functions), or a function of the issue for any i18n library: `messages={(issue) => t(`form.${issue.code}`, { ...issue.params, field: issue.label })}`, or `createFormMessages(t)`. Return `undefined` to fall back to the defaults, then to the schema's own message. `<FormField messages>` wins over the form's.
- **Issues.** `{ code, field, label?, params, message? }`. Codes: `required` (an empty value), `minLength`/`maxLength` and `minItems`/`maxItems` (`params.min`/`max`), `min`/`max`, `email`, `url`, `pattern`, `invalid` (no known validator; `message` is the schema's), `server` (a plain-text server error). A schema message that looks like a key (`"form.email.taken"`) is its own code, so schemas can carry translation keys. A server error may be `{ code, params?, message? }` instead of text: `{ fieldErrors: { email: { code: "email.taken" } } }`.
- **Schemas without codes.** Effect Schema (and any Standard Schema whose issues carry only `message` and `path`) reaches `messages` as `invalid`, or `required` for an empty value. Put the code in the message: `formIssueMessage(code, params)` writes `@@form:code` or `@@form:code|{json}` (a reserved prefix, so it never reads prose as a code), and the form reads it back as `issue.code` and `issue.params`, with `issue.message` `undefined`. Every code round-trips, built-in or dotted. The earlier `code|{json}` and bare dotted keys still read. Use a dotted key for your i18n library or a built-in code for the built-in dictionaries: `Schema.String.pipe(Schema.minLength(3, { message: () => formIssueMessage("minLength", { min: 3 }) }))`. Without a translation, the key shows without its params. There is no Effect adapter: its issues hold nothing more to read.
- **Actions.** `<FormActions submitLabel pendingLabel cancel onCancel secondaryAction>` stacks on narrow screens. For a busy state outside the form, `disabled` disables submit and cancel, `submitDisabled` only submit, and `pending` forces the pending look; with any of them the form doesn't submit, from Enter, code or an agent. `tone="destructive"` requires `confirm`, the sentence an agent must show a person; it becomes `data-agent-confirm` on the submit button.
- **In a dialog.** `FormDialog` takes the Form props plus `trigger` (or `open`/`onOpenChange`), `title`, `description`, `size`, `submitLabel`, `cancelLabel`, `pendingLabel`, `secondaryAction` and `returnFocus`. `onOpenChange(open, details)` and `onOpenChangeComplete(open, details)` (after the transition) say why in `details.reason`: `submit`, `cancel`, `escape`, `outside`, `dismiss`, or `trigger` when it opens. The body scrolls between the header and the actions; on narrow screens it is a bottom sheet. It closes when `onSubmit` resolves, and a thrown error keeps it open. Escape, outside presses and Cancel do nothing while pending. `confirmDiscard="Discard changes?"` (with `discardLabel`, `keepEditingLabel`) asks before closing with unsaved changes. `reviewStep={{ render: (values) => …, editLabel, confirmLabel }}` validates, shows a review, and runs `onSubmit` on confirm; a server field error returns to the fields. `prepare: async (values, { form }) => ({ values } | { error })` runs first with the submit pending. Returned `values` are reviewed and submitted and also written into the form (`setValue` per top-level key), so Edit shows them; they must pass the schema as input too. Or write through `form.setValue` and return nothing: the form's values are parsed again and reviewed. Returned `values` win over what `prepare` wrote. `editable: (state) => !state.error` hides Edit, and `title: (step) => step === "review" ? "Check the order" : "New order"` follows the step.
- **Instance.** Inside a `Form`, `useFormInstance<Values>()` is the typed react-hook-form instance (`trigger`, `setValue`, `getValues`, `control`, `formState`). Its `watch` re-renders the Form, not your component: use `useFormWatch(name)`. `useFormFieldArray(name, options)` wraps `useFieldArray`; key rows by `field.id` (or, when the items carry their own `id`, by the property `keyName: "fieldKey"` names) and name fields `` `tags.${index}.label` ``. `form-context.ts` is internal: import only from `@/components/ui/form`.
- **Steps.** `StepDialog` (or `StepForm` inline) splits one schema into `steps: { id, title, description?, render: (form) => …, fields?, validate? }[]`. Next and Enter validate only that step's fields (`fields`, or its mounted `FormField`s) and then `validate(values)`, which returns nothing or an error in any shape `onSubmit` throws. Back keeps values. The last step submits through `onSubmit`; a failed validation or a server field error returns to the step that holds the field. Focus moves to the step heading on Next and Back. The progress list marks the current step with `aria-current="step"`. `onStepChange(id, { index, previous, direction })`, `step`/`defaultStep`, and `labels` (`next`, `back`, `submit`, `progress`, `cancel`) in the page's language. Agents press Next, Back and the submit button by name. `StepDialog` `onOpenChange(open, details)` gives `details.reason` (`submit`, `done`, `cancel`, `escape`, `outside`, `dismiss`, `trigger`). To show the outcome in the dialog instead of closing it, pass `resultStep={{ title, render: (result, { close, restart }) => … }}`: `result` is what `onSubmit` resolved with, focus moves to the result heading, Done (`labels.done`) and Escape close it (reason `done` or `escape`), and `restart()` starts over from step 1 with the default values.
- **Label placement.** `labelPlacement` on `Form` sets a default for its fields, plain `Field`s inside it included; `labelPlacement` on a `FormField` or `Field` overrides it; see "Floating labels".
- **Agents.** Fields are their own UI SDK parts, so agents fill them by label. With a `label` (or `aria-labelledby`), the form itself offers `submit` and `reset`; a destructive form hides them so the gated button is the only way.

## Floating labels

`<Field labelPlacement="top" | "in" | "on">` (and `Form`/`FormField labelPlacement`) moves the `FieldLabel`. It stays a real `<label>`, so people, screen readers and agents name the control the same way in every placement.

- **`top`** (default): above the control.
- **`in`**: inside the control like a placeholder; it floats up and shrinks on focus, once the control has a value, or while its popup is open. The control grows by `--field-label-offset` to fit both, so nothing moves when it floats. A placeholder would sit under the resting label, so it shows only while the control is focused: write it as a format hint, never as the only instructions.
- **`on`**: on the control's top border, cutting the line. It is drawn over `--field-label-surface`, which cards (`field-label-surface-card`), dialogs and drawers (`field-label-surface-popover`) and floating surfaces set to their fill; the page background otherwise. Set it yourself on another coloured surface. Placeholders show as usual.
- **Controls.** Input, InputGroup (the label starts after a leading icon), Textarea, Select, NativeSelect, NumberInput, DatePicker, DateTimePicker, Combobox and TokenInput (it grows with its chips; `on` leaves room under the label). A Form's default reaches only those, in a `FormField` or in a plain `Field` inside the Form (a read-only Textarea, say) that doesn't set its own; Checkbox, Switch, RadioGroup, Slider, SegmentedControl and ToggleGroup keep their label on top. A control of your own floats on `:placeholder-shown`, `data-filled` or `data-open`: give its input `useFloatingPlaceholder(placeholder)` and add it to `floatingLabelControls` so a Form's default applies.
- **State.** The description and error stay below. An invalid field turns the label `destructive`; a focused one `foreground`. The motion is a transform, collapsed under reduced motion. The states come from the theme's `field-floated` variant, so update `@eskais/theme` with the components.

## Elevation

Surfaces (cards, columns, panels) use `shadow-surface`. Anything that floats (popover, menu, list popup, toast, dialog, a `Floating` bar) uses the floating level: `surface-floating`, or its parts `shadow-floating`, `rounded-floating`, `bg-floating`, `backdrop-floating`, `border-floating-border`. Tokens: `--floating-shadow`, `--floating-radius`, `--floating-backdrop`, `--floating-opacity`, `--floating-border`, `--floating-offset` (see AGENTS.md "Elevation"). The fill is translucent and blurred by default, opaque without `backdrop-filter` or with reduced transparency. `data-elevation="flat"` on any ancestor removes the depth. Never use viewport-height units (`vh`, `dvh`, `h-screen`) to place floating UI; it takes its position from its container.

## Separate the layers

- **Generic UI** (open/close, pending, focus, dismissal): UI SDK, already inside the components. Don't rebuild it with `useState` + `useEffect`.
- **Reusable app behavior** (confirm before deleting, search on Enter): an Eskais UI composed component such as `ConfirmDialog` or `SearchField`.
- **Business logic** (requests, toasts, cache invalidation): always in your callback (`onConfirm`, `onSearch`). Components never run side effects of their own.

## Agents

- Create one bridge in the app with `createAgent` from `@ui-sdk/react/agent`. Pass an `allow` that checks `step.confirm` and asks a person.
- `ConfirmDialog` with `tone="destructive"` requires `agentConfirm`: a sentence saying what confirming does. It becomes `data-agent-confirm`, so agents must get approval.
- `SearchField` exposes a `submit` action to agents only when `onSearch` is set.
- Show the approval prompt as its own alert dialog (`createConfirm` from `@ui-sdk/react/alert-dialog`), not as page content: when the agent opens a modal such as `ConfirmDialog`, the rest of the page goes inert and an inline prompt can't be clicked.
- Every control needs a name a person would recognize; the agent finds it by that name.
- Test every interface with the agent test from the ui-sdk skill (`references/agent-ready.md`).

## Style

- Use the variants (`variant`, `size`) and the semantic tokens: `background`, `foreground`, `primary`, `secondary`, `muted`, `accent`, `destructive`, `success`, `warning`, `info`, `border`, `input`, `input-strong`, `field`, `ring`, `overlay`, and `link`/`link-soft` for link text and a caret (4.5:1 on background, card and muted). `accent` is a surface (hover and selected fills) only: never a text colour or a stroke. For a stroke use `border-input-strong`, `border-primary` or `ring-ring`; for coloured text, `text-link`.
- Text fields take a soft `border-input` edge on a `bg-field` fill; checkboxes, radios and switch tracks, which nothing else identifies, take `input-strong` (3:1).
- Style state with UI SDK attributes: `data-pending`, `data-disabled`, `data-open`, `data-starting-style`, `data-ending-style`.
- Use the shape and density tokens instead of fixed sizes: `rounded-control`, `rounded-choice` (checkbox, textarea), `rounded-surface`, `h-control` (`-sm`, `-lg`), `shadow-surface`, and the spacing roles below. Surfaces that may turn glassy use `bg-<color>/(--glass-opacity)` and `backdrop-surface`.
- Theme and color scheme are app-level: `createAppearance({ colorScheme: "system" })` and `<Appearance appearance={…}>` from `@eskais/appearance` keep `.dark`, `data-color-scheme` and `data-theme` on `<html>` in sync; call `appearance.apply()` before the first render. Without any script the theme still follows `prefers-color-scheme: dark`, unless `<html>` has `data-color-scheme="light"` or `class="light"` (render one from the server for a saved light choice). The `dark:` variant does too: the theme item appends its `@custom-variant dark { … }` block below the one-line `@custom-variant dark (&:is(.dark *))` that shadcn writes, and Tailwind uses the last one, so keep it last. Don't add a theme prop to a component.
- Tones: `neutral`, `info`, `success`, `warning`, `destructive` say what a status means; `violet` is a category tone (a label or kind), never a status. For a tinted chip or surface use the soft tokens, `bg-{tone}-soft text-{tone}-soft-foreground border-{tone}-border`, not `bg-{tone}/10`; for a loading placeholder, `Skeleton` or `bg-skeleton`.
- Colour: set the seeds `--brand`, `--link-brand` (links and the caret, a blue by default), `--neutral-hue`, `--neutral-chroma` (and `--radius`) in `:root`; primary, its foreground, ring, accent and greys derive from them in light and dark. Or use a preset from `@eskais/palettes` with `data-palette="blue"` (`neutral`, `violet`, `green`, `orange`) on any element, or `createAppearance({ palette })`. To take over one colour, set that token in `:root` or `.dark`. Keep a custom brand at 4.5:1 on the background.
- Themes are attribute scopes, not separate components: `data-theme="compact"` or `data-theme="glass"` on any element, nested freely. A theme only sets tokens; never branch on the theme in a component.
- Pass layout classes (margin, width, grid placement) through `className`. To change how a component looks, edit its file in `components/ui/`, which you own.
- Optional: `npx shadcn add @eskais/lint-rules` adds an oxlint config with the `react` and `ui-tailwind` presets of `@p-otero/oxlint-rules` (hooks, React Compiler checks, `p-otero/spacing-tokens`) and the `@shadcn/lint` rules (`no-restyle`, `no-raw-colors`…). Extend it from `.oxlintrc.json`.

## Spacing

Pick spacing by the relationship between the things it separates, never by a number; each role tightens under `data-theme="compact"`.

| Utility                           | Role                                                                             |
| --------------------------------- | -------------------------------------------------------------------------------- |
| `gap-inline`                      | icon + text, or parts inside one control, chip or row                            |
| `gap-items`                       | siblings in a list or stack: cards in a column, chips, buttons, form fields      |
| `gap-group`                       | groups inside a surface: header vs body, dialog sections                         |
| `gap-section`                     | surfaces on a page                                                               |
| `px-inset-chip` / `py-inset-chip` | pills, badges, chips, kbd                                                        |
| `px-inset-item` / `py-inset-item` | menu and list items, small cards, table cells                                    |
| `px-control-x`                    | buttons, inputs, selects                                                         |
| `p-inset-surface`                 | cards, dialogs, panels, popovers (`p-surface` is an alias)                       |
| `p-control-inset`                 | the rim of a control-height bar around `-sm` items (tab list, segmented control) |

- `inline`, `items`, `group`, `section` and `inset-surface` work with any spacing utility (`p-inline`, `pb-group`, `-mx-inline`). The chip and item insets are `px-`/`py-` only; otherwise use the variable, as in `-mx-(--item-padding-x)`.
- Components never set their own outer margin; the parent spaces children with `gap-*`. Pass margin through `className` only when composing.
- Sizes (`size-*`, `h-*`, `w-*`) aren't spacing; prefer `h-control` and friends.
- In the registry, `p-otero/spacing-tokens` rejects numeric spacing (`gap-2`, `md:px-1`). The exceptions are `0`, `px`, and a disable comment that gives the reason.

## Tone

Status meaning has one vocabulary across Badge, Alert, StatusPill, StatusDot, Progress, Meter and Toast: `tone` is `neutral`, `info`, `success`, `warning` or `destructive` (`Tone` from `@/lib/tone`). Badge's `variant` is only its untoned look (`default`, `secondary`, `outline`); `variant="success"` and friends still work but are deprecated. A toast's tone comes from its type (`toastTone`: `error` is `destructive`).

## Toasts

- Place `<ToastStack />` once (or pass a `toaster` from `createToaster()`), and call `toast()`, `toast.success()`… from your handlers.
- Its close buttons are named "Dismiss". Pass `labels={{ close: "Cerrar" }}` in the page's language (`closeLabel` is deprecated).
- Each type leads with a decorative icon in its tone colour: `info` a circled i, `success` a check, `warning` a triangle, `error` a circled exclamation mark, `loading` a spinner, and `default` none. It is `aria-hidden`, so the title has to say what happened. In your own `Toast` composition, render `<ToastIcon type={item.type} />` before the title.
- The region takes no pointer events: only the toasts themselves cover the page, so buttons beside or behind the stack stay clickable.
- Timers pause while focus is in a toast, and while the pointer rests on one for `hoverDelay` ms (300 by default). A pointer that only passes over doesn't hold them.

## Testing toasts and alerts

UI SDK announces toasts through two visually hidden live regions it appends to `<body>`: `role="status"` (polite) and `role="alert"` (assertive), both marked `data-ui-sdk-announcer`. They stay for the page's life and keep the last text they announced, so after a toast closes `getByRole("alert")` and `getByText("Saved")` can still find its copy there.

- Find a toast by its part, not by text on the whole page: `[data-slot="toast"]`, or `within(screen.getByRole("region", { name: "Notifications" }))` while a toast is showing (the region is only a landmark then).
- `npx shadcn add @eskais/test-utils` adds the helpers to `lib/test-utils.ts`. It needs `@testing-library/dom` (a dev dependency).
  - `getToast(text)` / `queryToast(text)`: the showing toast with an element whose text matches; both throw when several match, `getToast` also when none does. `queryToasts()` lists them, newest first, without toasts animating out.
  - `queryAlerts()` / `queryStatuses()`: `role="alert"` / `role="status"` elements without the live regions.
  - `isAnnouncer(node)`: whether a node is in a live region. `ignoreAnnouncer` is an `ignore` for text queries: `screen.getByText("Saved", { ignore: ignoreAnnouncer })`.
  - `readAnnouncements()`: `{ polite, assertive }`, what the live regions hold. A toast is announced about 200ms after it shows.
  - `resetAnnouncer()`: removes the live regions; UI SDK makes new ones on the next announcement. UI SDK exports no reset of its own, so call it in `afterEach`, after Testing Library's `cleanup`.

## Layers and motion

Stack with `z-sticky` < `z-overlay` (dialogs) < `z-popover` < `z-toast`, never a number. Time transitions with `duration-micro` (140ms: hover, popovers, tooltips), `duration-panel` (180ms: accordion, sidebar, toasts) or `duration-dialog` (200ms), with `ease-standard`. Reduced motion is handled globally by the theme.

## Touch targets

On touch screens (`pointer: coarse`) buttons, toggles, tabs, segmented items, checkboxes, radios and switches get an invisible hit area of at least 44px (`--control-height-touch`); sidebar items and label rows around a choice grow to 44px. Desktop looks the same. Give a new small control the `touch-target` class; where controls stack tighter than 44px, grow the row with `pointer-coarse:min-h-(--control-height-touch)` instead.

## Narrow screens

`narrow:` applies at 760px viewport width and below (`flex-row narrow:flex-col`). It is unrelated to the `compact` density theme, which changes sizes at any width. Prefer container queries for components placed in panels of different widths.

## Typography

Pick text size by role, not by number: `text-meta` (eyebrows; with `tracking-meta`, uppercase if you want), `text-caption`, `text-body-sm`, `text-body`, `text-title-sm` (card titles), `text-title` (dialog titles), `text-display-sm` (page titles, stat values), `text-display`, and `text-entry` for text a person types (16px on touch screens, so iOS doesn't zoom into a focused field; never set `maximum-scale` or `user-scalable=no` instead). Each sets size, line height and weight, and tightens under `data-theme="compact"`; see AGENTS.md "Typography" for the values. `tracking-tight` (-0.012em) suits titles; `font-mono` is Geist Mono (installed by `font-geist`).

## Icons

Components import their icons from `lucide-react` by name (`ChevronDownIcon`, `XIcon`, `CheckIcon`, `SearchIcon`…), and every item that does lists it in `dependencies`, so shadcn installs it. Browse the set on lucide.dev; the site's Icons guide shows the ones the registry uses.

- **Decorative**: lucide sets `aria-hidden` unless the icon gets an `aria-*`, `role` or `title` prop, so an icon beside text needs nothing. An icon-only button is named by the button, and shows that name in a tooltip: `<Button size="icon" aria-label="Delete"><TrashIcon /></Button>`.
- **Meaningful**: when nothing else says it, `<Icon icon={TriangleExclamationPointIcon} label="Blocked" />` renders `role="img"` with that name. `Icon` takes any SVG component.
- **Size**: controls set it (`[&_svg]:size-4` in Button, Toggle, menu items, inputs; `size-3` in Badge), and those classes beat lucide's `size` prop. Elsewhere: `size-3.5` beside `text-body-sm`, `size-4` beside `text-body`, `size-5` beside a title. Unsized, an icon is 24px.
- **Colour**: `currentColor`; use a tone's text colour (`text-success`), and still say the status in words. Alert colours its first-child icon by tone; Toast draws its tone's icon itself.
- **Swap the set**: only the import lines change. In the registry, `eskais/no-inline-icons` flags hand-drawn `<svg>`; drawings that aren't icons (spinner, status rings) disable it with a reason.

## Add a component to the registry

1. Read the UI SDK page for the component. If UI SDK ships it, style its parts; don't reimplement.
2. If it doesn't, write a primitive with `definePrimitive` (`agent.actions` last) next to the component, as `search-field-primitive.ts` does, and render it with `createParts`.
3. Never give a `registry/lib` file and a `registry/ui` file the same basename: `shadcn add` rewrites imports by basename and points one at the other in the consumer.
4. Use `cnState` from `@/lib/utils` so a consumer's `className` can still be a function of state.
5. Size and shape it with the tokens above so every theme applies.
6. Add tests in `test/`: behavior with Testing Library, `mount`/`checkServer` for primitives, the agent test, and `allow` refused/approved for anything with `data-agent-confirm`.
7. Add the item to `registry.json`, run `bun run verify` and commit `public/r`.

## Keep it small

- Keep components short; split a file before it passes about 200 lines.
- Every screen state needs a decision: loading, empty, error, disabled, confirming.
- No `App*` wrapper layer and no providers the consumer must mount.
